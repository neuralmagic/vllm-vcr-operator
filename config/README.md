# vllm-vcr-operator manifests

Kustomize manifests for installing the operator into a CPU-only Kubernetes
cluster. Everything here is install configuration: no Go code, and no
operator-generated resources (the device-plugin DaemonSet is created by the
operator from the `SimulationEnvironment`, never by these manifests).

## Layout

| Path | Contents |
| --- | --- |
| `config/crd/bases` | `SimulationEnvironment` CRD, generated by controller-gen from `api/v1alpha1`. Never hand-edit. |
| `config/rbac` | Manager ServiceAccount, cluster role/binding, namespaced leader-election role/binding. |
| `config/manager` | Manager Deployment (leader election, metrics/probe ports, webhook port, certificate volume, image env vars). |
| `config/webhook` | Webhook Service plus the Pod mutating and `SimulationEnvironment` validating registrations. |
| `config/certmanager` | Optional cert-manager `Issuer` + `Certificate` for the webhook serving certificate. |
| `config/default` | Composition of the above plus the cert-manager CA-injection patch. |
| `config/overlays/local` | `config/default` plus the samples, with `dev` image tags. |
| `config/samples` | The singleton `SimulationEnvironment` and an unchanged GPU-requesting llm-d modelserver. |
| `hack/install.sh` | Build the manifests and apply them in dependency order. |
| `hack/verify-manifests.sh` | Cluster-free verification (also run in CI). |
| `hack/kind-up.sh` | Optional local kind cluster; fails clearly when Docker is unavailable. |

## Install order

`hack/install.sh` (or `kubectl apply -f <(kustomize build config/default)`)
applies two phases:

1. the operator namespace, the `SimulationEnvironment` CRD, RBAC, the webhook
   Service, the cert-manager `Issuer`/`Certificate`, and the manager Deployment;
   then it waits for the CRD to be `Established` and the manager rollout to
   succeed (the manager does not start without the certificate Secret);
2. the webhook registrations. Both are `failurePolicy: Fail`, so applying them
   before the webhook Service has endpoints would reject Pod creation
   cluster-wide for that window; `hack/install.sh` therefore never applies them
   until the manager is available. If you apply the whole build by hand, apply
   the two `*WebhookConfiguration` objects last.

Then apply a `SimulationEnvironment` (`kubectl apply -k config/samples`) and
label the nodes you want simulated:

```bash
kubectl label node <node> vcr.opendatahub-io/simulation=true
```

The label must match `spec.simulationNodes.nodeSelector` in the environment; only
matching nodes receive the synthetic GPU device plugin.

## Required Secrets

| Secret | Namespace | Required? | Purpose |
| --- | --- | --- | --- |
| `vllm-vcr-operator-webhook-server-cert` | `vllm-vcr-operator-system` | yes | Webhook serving certificate (`tls.crt`, `tls.key`, `ca.crt`). Created by cert-manager, or pre-created by hand. |
| Secrets named in `spec.imagePullSecrets` / `spec.profiles[].pullSecretName` | `vllm-vcr-operator-system` | only for private profile images | Pull credentials for profile OCI images. Values are copied into an operator-managed Secret in the workload namespace; they never appear in annotations, status, events, or logs. |

No other Secret is needed: the operator reads no global configuration file and
holds no credentials of its own.

## Webhook certificates

Two supported paths. The manager mounts the certificate at
`/tmp/k8s-webhook-server/serving-certs` from Secret
`vllm-vcr-operator-webhook-server-cert`; it does not start until that Secret
exists.

**cert-manager (default).** `config/default` includes `config/certmanager` and
patches both registrations with

```yaml
cert-manager.io/inject-ca-from: vllm-vcr-operator-system/vllm-vcr-operator-serving-cert
```

so cainjector fills `caBundle` from the issued certificate. The two halves of
that annotation are rewritten from the `Certificate` object itself
(`replacements` in `config/default/kustomization.yaml`), so an overlay that
changes the operator namespace stays correct. If cert-manager is not installed,
the install fails while applying `Certificate`/`Issuer`; use the second path.

**Pre-created Secret (no cert-manager).** Create the namespace and the serving
certificate first (the manager Pod does not start without the Secret), then
install without the cert-manager objects; `hack/install.sh` publishes `caBundle`
from the Secret for you.

```bash
# 1. namespace + serving certificate (SANs must match the webhook Service)
kubectl create namespace vllm-vcr-operator-system --dry-run=client -o yaml | kubectl apply -f -
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout tls.key -out tls.crt -subj "/CN=vllm-vcr-operator-webhook-service.vllm-vcr-operator-system.svc" \
  -addext "subjectAltName=DNS:vllm-vcr-operator-webhook-service.vllm-vcr-operator-system.svc,DNS:vllm-vcr-operator-webhook-service.vllm-vcr-operator-system.svc.cluster.local"
cp tls.crt ca.crt
kubectl -n vllm-vcr-operator-system create secret generic vllm-vcr-operator-webhook-server-cert \
  --from-file=tls.crt=tls.crt --from-file=tls.key=tls.key --from-file=ca.crt=ca.crt

# 2. install without cert-manager; the script patches caBundle from ca.crt
hack/install.sh --no-cert-manager
```

If you apply the manifests by hand instead of using the script, you must add
`caBundle` (base64 of `ca.crt`) to both webhook configurations yourself:

```bash
ca_bundle="$(base64 -w0 ca.crt)"
kubectl patch mutatingwebhookconfiguration vllm-vcr-operator-mutating-webhook \
  --type=json -p "[{\"op\":\"add\",\"path\":\"/webhooks/0/clientConfig/caBundle\",\"value\":\"${ca_bundle}\"}]"
kubectl patch validatingwebhookconfiguration vllm-vcr-operator-validating-webhook \
  --type=json -p "[{\"op\":\"add\",\"path\":\"/webhooks/0/clientConfig/caBundle\",\"value\":\"${ca_bundle}\"}]"
```

Renewing the certificate means updating the Secret and the two `caBundle`
values; that is the reason cert-manager is the documented default.

## Webhook registration

| Registration | Path | Scope | Policy |
| --- | --- | --- | --- |
| `vllm-vcr-operator-mutating-webhook` (`pod-mutator.vcr.opendatahub-io`) | `/mutate-v1-pod` | Pods, `CREATE` | `failurePolicy: Fail`, `sideEffects: None`, `matchPolicy: Equivalent`, `admissionReviewVersions: [v1]` |
| `vllm-vcr-operator-validating-webhook` (`simulationenvironment-validator.vcr.opendatahub-io`) | `/validate-vcr-opendatahub-io-v1alpha1-simulationenvironment` | `simulationenvironments`, `CREATE`/`UPDATE` | `failurePolicy: Fail`, `sideEffects: None`, `matchPolicy: Equivalent`, `admissionReviewVersions: [v1]` |

The paths must match the constants `internal/webhook` registers. The mutating
registration excludes the operator namespace
(`kubernetes.io/metadata.name NotIn [vllm-vcr-operator-system]`) so the
operator's own Pods are never translated. `reinvocationPolicy` is deliberately
unset (defaults to `Never`): admission is idempotent, so a second invocation
after another mutating webhook has nothing to do.

The registrations are hand-written rather than generated from kubebuilder
markers, because `failurePolicy`, the namespace selector, and CA injection are
install decisions. `hack/verify-manifests.sh` fails if controller-gen starts
emitting `config/webhook/manifests.yaml` from markers, so the two sets can never
silently diverge.

## Images

All image references are env-injected, so a single operator build serves every
cluster. Change them in an overlay (see `config/overlays/local`) or with
`kubectl -n vllm-vcr-operator-system set env deployment/vllm-vcr-operator-controller-manager ...`.

| Env var | Default (placeholder) | Built by | Used for |
| --- | --- | --- | --- |
| `VCR_FRONTEND_IMAGE` | `quay.io/opendatahub/vllm-vcr-frontend:v0.33.0-cpu` | `Dockerfile.supervisor --target frontend` | Python vLLM frontend container: serves the original inference port. |
| `VCR_BACKEND_IMAGE` | `quay.io/opendatahub/vllm-vcr-backend:v0.33.0` | vllm-vcr's own Dockerfile | `vllm-vcr play` simulator container. |
| `VCR_DEVICE_PLUGIN_IMAGE` | `quay.io/opendatahub/vllm-vcr-device-plugin:v0.33.0` | `Dockerfile.device-plugin` | DaemonSet that advertises synthetic `nvidia.com/gpu`. |
| `VCR_SUPERVISOR_IMAGE` | `quay.io/opendatahub/vllm-vcr-supervisor:v0.33.0` | `Dockerfile.supervisor` (default target) | `vcr-supervisor` binary; the frontend image embeds the same binary at `/usr/local/bin/vcr-supervisor`. |
| `VCR_MANAGER_IMAGE` (only used by `hack/kind-up.sh`) | — | `Dockerfile` | Manager image to preload into a kind cluster. |

None of these images is published yet: the defaults are valid references under
the project's public registry namespace, never a private registry, and every one
of them is overridable without rebuilding the operator. Profile images are not
operator images: they come from `spec.profiles[].image` and are produced by the
separate profile repository (`docs/contracts/profile-image.md`).

Image build notes:

- `Dockerfile` (manager) and `Dockerfile.device-plugin` cross-compile from the
  build platform, so `docker buildx build --platform linux/amd64,linux/arm64`
  works without QEMU for compilation.
- The device plugin must be able to create its socket in the kubelet
  device-plugin directory (`/var/lib/kubelet/device-plugins` by default), which
  is a root-owned hostPath. The operator-rendered DaemonSet grants that access
  (uid or `fsGroup`); the image itself needs no NVIDIA capability, device, or
  runtime class. If the socket directory is not writable the container exits
  non-zero and crash-loops visibly instead of advertising nothing.
- `Dockerfile.supervisor` has two targets: `frontend` (CPU vLLM frontend plus
  the supervisor, what `VCR_FRONTEND_IMAGE` must point at) and `supervisor`
  (default; the binary alone, used as a COPY source). The `frontend` target needs
  `--build-arg FRONTEND_IMAGE=<cpu frontend image>`; its default
  (`python:3.12-slim`) contains no vLLM and exists only so the Dockerfile builds
  standalone.

```bash
docker build -t quay.io/<you>/vllm-vcr-operator:dev .
docker build -f Dockerfile.device-plugin -t quay.io/<you>/vllm-vcr-device-plugin:dev .
docker build -f Dockerfile.supervisor -t quay.io/<you>/vllm-vcr-supervisor:dev .
docker build -f Dockerfile.supervisor --target frontend \
  --build-arg FRONTEND_IMAGE=<cpu vllm frontend image> \
  -t quay.io/<you>/vllm-vcr-frontend:dev .
```

## RBAC

`config/rbac/role.yaml` is the ClusterRole `manager-role`. It is generated by
controller-gen from the kubebuilder markers in `api/`, `internal/controller`, and
`internal/webhook` (`make manifests`) and is checked in. The rule set must stay
a superset of the operator's needs:

| Resource | Verbs | Why |
| --- | --- | --- |
| `pods` (cluster-wide) | get, list, watch | Any namespace's GPU-requesting Pod is an admission candidate. Pods are never written through the API: the patch goes in the AdmissionReview. |
| `secrets` | get, list, watch, create, update, patch, delete | Read the operator-namespace pull-secret sources; create/update the operator-managed copy in the workload namespace. |
| `nodes` | get, list, watch | Skip nodes that already advertise `nvidia.com/gpu` from a real provider. |
| `apps/daemonsets` | get, list, watch, create, update, patch, delete | The synthetic GPU device plugin DaemonSet is operator-owned. |
| `simulationenvironments` | get, list, watch, update, patch | Read the singleton configuration; write finalizers. |
| `simulationenvironments/status` | get, update, patch | Publish reconciled profile metadata for admission. |
| `events` | create, patch | Reconcile diagnostics. Never contains Secret values. |

Leader election is a namespaced `Role` restricted to the single lease
`vllm-vcr-operator.vcr.opendatahub-io` (the `LeaderElectionID` in
`cmd/manager/main.go`).

`hack/verify-manifests.sh` fails when a required (apiGroup, resource, verb) tuple
disappears from the built output, so regenerating RBAC can never silently drop a
permission.

## Samples

- `vcr_v1alpha1_simulationenvironment.yaml` — the only valid environment,
  named `default`: node selector, 8 synthetic H200s per node, a placeholder
  profile image, and real CPU/memory sizing.
- `llmd-modelserver-deployment.yaml` — an **unchanged** GPU-requesting llm-d
  modelserver (`mock-prefix-cache`, llm-d labels and probes kept, `nvidia.com/gpu`
  requested). It has no simulator opt-in label, annotation, or container:
  admission detects the GPU request. Applied without the operator it stays
  `Pending`, which is the intended demonstration of why the operator exists.

Neither sample is part of `config/default`; `config/overlays/local` adds them.

## Verification

```bash
hack/verify-manifests.sh            # kustomize build, install set, RBAC, CRD idempotency, CI workflow
hack/verify-manifests.sh --kubectl  # additionally kubectl apply --dry-run=client
kustomize build config/default | less
make manifests && git diff --stat config/crd   # must be empty
```

`hack/verify-manifests.sh` needs `yq` (mikefarah v4) and `kustomize` (or
`kubectl kustomize`); the CRD idempotency check needs `controller-gen` at
`$(go env GOPATH)/bin/controller-gen` (override with `CONTROLLER_GEN`). The CI
workflow `.github/workflows/ci.yaml` runs the same script.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| Manager Pod in `CreateContainerConfigError` | Secret `vllm-vcr-operator-webhook-server-cert` is missing (cert-manager not installed and no pre-created Secret). |
| `no matches for kind "Certificate"` during install | cert-manager is missing: install it, or use `hack/install.sh --no-cert-manager`. |
| Applying a GPU workload is denied with a settings message | Working as designed: unsupported settings are rejected rather than approximated. The message names the setting. |
| Modelserver Pod stays `Pending` | No node carries the label selected by `spec.simulationNodes.nodeSelector`, or the device plugin DaemonSet is not Ready (see the environment's conditions). |
